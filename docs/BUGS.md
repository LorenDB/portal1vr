# Bug log

Severity: 1 = crash, hard lock, or nausea; 2 = feature broken; 3 = wrong with a workaround; 4 = polish or performance.
Bugs stay open until a headset playtest verifies the fix.

Earlier headset findings are recorded in the README and docs/avatar-verification.

| BUG-001 | 2 | 2026-10-06 full Portal playthrough | escape_02 ending: the player stays on the floor instead of floating up as GLaDOS is pulled into the ceiling. | The map lifts the player with a zero-gravity trigger plus a `point_clientcommand` sending `+jump`/`-jump`. `Hooks::dCreateMove` cleared `IN_JUMP` whenever the VR Jump action was not held, so the map's jump never happened, and a 21 u/s `trigger_push` alone cannot unstick a grounded player. | Fixed (jump now only adds). **Verified 2026-10-07** in the headset: the player floats up with GLaDOS. |
| BUG-002 | 2 | 2026-10-06 full Portal playthrough | After the final cutscene the screen stays black and "Still Alive" never plays. | The credits are a 2D HUD element (`CHudPortalCredits`) whose Paint starts the song, scrolls the lyrics, and ends the roll. The eyes are drawn without the HUD, and with `RenderWindow=0` no pass painted it at all. (With the window on, they would have played on the monitor only.) | `credits.h` reads the client's rolling-credits flags; while they are set, the desktop pass is drawn and shown on the flat screen in the headset. Playtest 2026-10-07: detection fired (`End credits rolling`), the song played and the credits showed on the desktop monitor, but nothing showed in the headset. Suspected: the flat screen is blended by the backbuffer's alpha, which the world pass fills with depth. The credits screen now ignores texture alpha, and flat-screen show/hide is logged with its reason and OpenVR results. **Verified 2026-10-07** in the headset (quick check: `ent_fire relay_blackout trigger` in escape_02); the credits are visible on the flat screen. |
| BUG-003 | 2 | 2026-10-06 full Portal playthrough | Walking in the room felt janky; the view sometimes seemed to lag the walk. | Three roomscale-follow faults: (a) the body's movement was taken out of the head offset a frame late, so the camera surged ahead by up to 1.3 units as the body started and stopped; (b) only movement along the current follow direction was handed over, so walking a curve or turning a corner let the body's sideways momentum drift the camera off the head by up to 20 units; (c) a head leaning through a wall portal near its edge steered the body into the wall beside the opening (pinned for 20 s at 21:45 in that log). | Fixed in `roomscale.h` (render-time credit, follow momentum model, steering into the opening); frame-pacing log added to rule out reprojection. **Verified 2026-10-07**: walking reported fine; the test-chamber log shows regular follow/idle cycles and no blocked follows. |
| BUG-004 | 2 | 2026-10-07, from SteamVR's `vrcompositor.txt` | The game misses the headset's frame rate, and SteamVR on Linux does not reproject, so missed frames repeat; positional movement judders and lags. | Full playthrough (2026-10-06): application CPU 10.8 ms / GPU 11.4 ms average against 11.1 ms at 90 Hz, 112,000 of 273,000 frames repeated, 473 timeouts. escape_02 (2026-10-07): CPU 21.5 ms / GPU 22.5 ms; a test chamber the same evening: CPU 18.3 ms / GPU 18.7 ms, 63% of frames repeated. On an RX 9070 XT, two 2624x2740 eyes of Portal should take a few milliseconds, so render resolution is unlikely to be the limit. More likely suspects: Source draws every eye and portal view on one thread (`mat_queue_mode 0`), and the DXVK present path calls `WaitDeviceIdle()` every frame, so the CPU and GPU never work in parallel. | In progress. Found: every run on 2026-10-07 had `RenderWindow=1` (installed config changed 2026-10-06 22:39), a third scene render per frame; the 10.8 ms playthrough had it off. And DXVK acquires desktop swap-chain images with an infinite wait, on the game thread and again on its submission thread, which `WaitDeviceIdle()` waits on: a FIFO desktop swap chain would pace the headset at the monitor's rate (today's compositor stats show exactly 60 frames a second). Done (awaiting playtest, PLAYTEST-framerate): `RenderWindow=2` mirrors the left eye with one GPU copy (new default; installed); in VR the desktop present never waits for a swap-chain image and skips the frame instead; the desktop present mode is logged; a `Frame time` line every 10 s splits frames into engine, eyes, desktop, present, command thread, GPU wait, submit and pose wait. Run 2026-10-07 20:02 (mirror on): the desktop swap chain is IMMEDIATE, so the monitor never paced the headset; the mirror works. The headset runs at 120 Hz (8.33 ms). Frames took 33.3 ms (every fourth refresh, 30 fps): CPU work about 4.5 ms in all (engine 1.3-2.0, eyes 1-1.8 each, desktop 0), then 17-19 ms waiting in `vkDeviceWaitIdle`, then about 11 ms in `WaitGetPoses`. The GPU wait did not follow scene cost, and the 9070 XT runs the `BOOTUP_DEFAULT` power profile at `auto`. Added GPU timestamp queries (`GPU time` line: our GPU work per eye, desktop, after-render and present, and the gap between frames) to tell low clocks from a blocked queue. Run 20:57 (GPU timestamps): left eye 1.2-2.1 ms, right 1.2-1.9 ms, mirror 0.08 ms on the GPU, but the desktop present 19-21 ms. GPU at 1.3-1.5 GHz and 24% busy, so not clocks. Cause: under XWayland the desktop swap chain hands out an image before the compositor has released it; DXVK's present command buffer waits on the acquire semaphore, which stalls the whole graphics queue (and the next headset frame behind it) until the desktop compositor lets go. A fence check (desktop present skipped until the image is truly free) went in, but the 21:46 run never skipped and the present span stayed 21-22 ms with the GPU 74% idle: the images were free, so the stall is not the acquire wait. Likelier: `vkQueuePresentKHR` itself (Wine/XWayland) blocks DXVK's submission thread about 20 ms, delaying every submission behind it. Now measured directly (`Desktop window system:` line, present and acquire time on the submission thread), and `RenderWindow=0` skips desktop presents during play to show the gain. Awaiting playtest. |
